# DSH 学习小组 · 第二期周报

**2026 年 10 月 25 日｜第二期**

> 本期主题：如何设计一个可维护、可持续进化的 Skill？

上一期，我们讨论了「少许愿，多提炼」，尝试把实际工作中积累的经验整理成 AI 能够使用的方法。

Skill 可以承担这个工作。但经验越积越多，新的问题也随之出现：规则不断增加，旧经验可能不再适用，Agent 需要阅读的指令也越来越长。

本周，我们研究了如何让 Skill 保持精简，同时能够随着实践不断更新。

## 如何设计一个可维护的 Skill？

### 先决定什么值得写进 Skill

按照 [Agent Skills 开放规范](https://agentskills.io/specification)，Skill 通过名称和描述让 Agent 识别适用任务，在 `SKILL.md` 中提供执行指导，并可以附带参考资料和脚本。

但并不是所有经验都适合放进去。通用的思考方法、项目约束和单次任务的信息，都有各自更合适的存放位置。代码格式可以交给 Linter，数据结构可以交给 Schema，确定性的行为可以通过测试约束。Skill 更适合保存需要结合实际情况作出判断的专业经验。

写入一条规则之前，值得先问一句：**如果删掉它，AI 的工作结果会变差吗？** 如果答案是否定的，这条规则可能根本不需要存在。

### 压缩指令，保留研究过程

本周整理的 [Skill Design Method](https://github.com/Ri0n72Y/agent-identity/blob/main/docs/skill-design.md) 主张保留完成任务所需的最小充分指令。

我们采用的组织方式是：

- `SKILL.md` 保存适用条件、关键判断和必要的工作方法。
- 运行参考资料保存专业规范、技术细节与案例，供 Agent 按需读取。
- 研究档案保存资料来源、争论、被否决的方案，以及当初作出判断的理由。

后两类材料可以放在 `references/` 中，但不必全部在日常执行时加载。

**为什么要保留研究档案？**

因为 Skill 本身是一种知识压缩。我们把调查和讨论中得到的经验提炼成几条规则，原本的论证过程就消失在运行指令之外了。

短期内，这有利于节约上下文；但过了一段时间，我们可能已经不记得某条规则为什么存在，更无法判断它是否应该修改。

保留研究资料，就是给未来的自己留下重新审查这些规则的依据。

不过，也没必要为了文件分层而强行拆分内容。如果一小段知识几乎每次执行都要读取，直接留在 `SKILL.md` 中更省事。

### 让实践不断修正 Skill

Skill 没必要一开始就写得面面俱到。先投入使用，发现问题，再针对问题修改规则，通常比预先制定一整套复杂流程更有效。

本周的 [Dependency Risk Testing Skill](https://github.com/Ri0n72Y/agent-identity/blob/main/.agents/skills/dependency-risk-testing/SKILL.md) 就有一个实际案例。

在 [DSH Meeting 插件项目](https://github.com/Ri0n72Y/dsh-meeting)中，我们发现一些自动化测试重复检查相同的边界，还有一些测试依赖人为模拟的内部状态。大量的CI全部通过，**但实际上只是在反复验证确定的边界，既不是单元测试，也不是有意义的标准测试。** 这是ChatGPT常见的防御式编程，但又没防御到点子上，只是白白浪费CI资源。

调查过程中参考的软件测试理论、不同意见以及具体反例，则保存到了[研究档案](https://github.com/Ri0n72Y/agent-identity/blob/main/.agents/skills/dependency-risk-testing/references/research-history.md)。日常编写测试时不需要反复阅读这些材料，只有重新审查方法时才需要调取。

这一实践也提醒我们，Skill 的更新不应该只有增加规则这一种方式。旧规则不再有效，就应当修改；如果删除某条指令并不会让执行结果变差，那就没有必要继续保留。

对于已经编写好的 Skill，我们还需要通过独立任务检查它能否正确触发，并观察它是否确实改变了 Agent 的行为。文件能够加载、规则写得合理，都不能单独证明它有效。

## 本周其他分享：React 组件的推荐写法

本周还分享了 [React Component Coding Skill](https://github.com/Ri0n72Y/agent-identity/blob/main/.agents/skills/react-component-coding/SKILL.md)，主要讨论 React 组件中业务逻辑与展示逻辑的分离。

对于职责较复杂的组件，可以让功能组件负责数据获取、业务状态和操作编排，私有 View 组件通过 props 接收数据与回调，专注于界面展示。

但简单组件没有必要强制拆分，专属 View 通常也可以留在同一个文件中。我们希望 Agent 能够根据实际复杂度决定如何组织代码，而不是遇到任何组件都机械套用一套结构。
